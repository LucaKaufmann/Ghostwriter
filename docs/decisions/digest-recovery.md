# Digest recovery contract: observed boundaries and next change

Status: investigation, 2026-09-27. Base `679bd909d5780e55be21d8ea5347e3ea6a9a54d3` (INGEST-01 on ENV-01). This note records current behavior, not a new public retry policy. The executable evidence is `ghostwriter/tests/test_bindery_recovery.py`; its isolated SQLite database, synthetic article/transcript and artifact, mocked remotes, disabled schedules and network guard make no provider or external calls. `test_bindery_seen_articles.py` already proves a failure before EPUB creation does not save `SeenArticle`; that proof is reused rather than duplicated.

## Current sequence

`generate_digest()` inserts a `processing` Digest with a 30-minute timestamp lock, then schedules an in-process task. Scheduled generation records `last_run_at` when the task **starts**, not when the edition completes (`scheduler.py`). `BinderyPipeline.run()` writes an EPUB, commits DigestArticle groups separately, commits media `consumed_at`/`consumed_digest_id`, attempts Gmail and Wallabag remote processed markers (errors are swallowed), then `_complete()` commits completed status and queued seen rows together. Each step can leave earlier output durable. An ordinary `Exception` marks the digest `failed` and logs a pipeline failure; `asyncio.CancelledError` bypasses this handler. Startup marks all `processing` digests failed with `Cleared on restart`, without reconciling files, article rows, consumed media or remote state. Podcast startup similarly marks running episodes failed; digest recovery does not resume either pipeline.

The tests inspect the job row, article and seen rows, media owner, artifact file, remote mock and pipeline failure event after each boundary. Failures before the final transaction commits leave `article_count=0` and `stage=compiling`, although later failures can have three article rows and an EPUB. If `pipeline_completed` logging raises **after** the final transaction commits, the exception handler changes the already published Digest back to `failed`: it retains `article_count=3`, `stage=completed` and two committed seen rows. The `failed` event reports the current stage, not which durable steps committed. The API's completed-only listing will not surface either failed edition as completed.

| Injected boundary | Failed job's durable state | Fresh job retry with same source mocks |
| --- | --- | --- |
| Artifact generation raises | No EPUB, article or seen rows; media unconsumed; remotes unmarked | Produces three rows and an EPUB. This is the pre-output case covered more fully by existing seen-article tests. |
| Newsletter article save raises after Wallabag save | EPUB and one Wallabag row survive; no seen rows or media claim; remotes unmarked | Produces all three again. Earlier failed row and EPUB remain, so duplicate stored output accumulates. |
| Media `consumed_at` update fails at commit | EPUB and all three rows survive; media unconsumed; remotes unmarked; no seen rows | Produces all three again; failed output remains. |
| Final transaction's `Session.commit()` raises before commit | EPUB and all three rows survive, media points to failed digest, both mock remotes marked; final status/count/seen updates roll back | Completes with zero articles and no EPUB in this fixture. The source content remains in the failed digest's rows/file but is absent from the successful retry. |
| `pipeline_completed` logger raises after final commit | EPUB, all three rows and two seen rows committed; exception handler changes Digest to `failed` while leaving `article_count=3`, `stage=completed`; media and mock remotes marked | Completes empty in this fixture. This is a false failure after local publication, and its already committed seen rows also prevent rediscovery. |
| Gmail/Wallabag marker calls raise, with mock effect either absent or applied before error | Both cases complete with three rows, EPUB, media consumed and two seen rows. One mock leaves markers absent; the other applies them and then raises as if the response were lost. | A later job completes empty in both cases. The thrown error does not establish the remote outcome, and no durable pending-ack retry exists. |
| `CancelledError` inside final commit, then startup recovery | Before startup: `processing`, EPUB and three rows, media assigned, mock remote markers applied; final transaction rolled back. After lifespan startup: `failed` with `Cleared on restart`; durable output unchanged. | A fresh job cannot reconstruct consumed/acknowledged sources in this fixture. The test invokes the real lifespan recovery against a disposable DB; it does not kill an OS process. |
| `CancelledError` in completion logger after final commit | Digest remains `completed` with count 3, seen rows, EPUB and media assignment; exception handler does not run. | No restart recovery is needed for this committed Digest, despite the cancelled task. |
| Fresh versus >30-minute lock | Fresh `processing` row blocks a new job. Old timestamp is changed to `failed` with `Stale lock released`, then a new `processing` row is inserted. | There is no heartbeat/owner check or cancellation of an old in-process task; the 30-minute cutoff is admission policy, not a lease protocol. |

Failure at a remote marker does **not** fail the job. The remote outcome is unknown from the exception: our two deterministic mocks cover no effect and effect followed by lost response. The actual Wallabag operation archives before adding the processed tag, so a tag error can occur after an archive change; a Gmail success response can likewise be lost. A completed local edition has no durable marker retry path in either mock outcome. Conversely, if a marker succeeds and completion fails, a new digest cannot rely on remote replay. Exact-once remote behavior cannot be inferred from these tests or guaranteed by local SQLite alone.

## Implementation-ready follow-up: atomic local publication and durable acknowledgement intent

One bounded backend PR should make a digest's local publication an explicit commit boundary: after EPUB generation, save all article rows, queued seen rows, media consumption and completed Digest state in one SQLite transaction. On a failed commit, the media and seen claims must roll back and a new job may retry; an abandoned EPUB can be cleaned separately under the retention contract. Move remote processed calls after that commit. Persist per-source acknowledgement intent in the same transaction, then retry pending acknowledgements on a subsequent single-process run/startup until success. A successful remote call followed by a crash before marking intent done may call the provider twice, so the provider operation must be treated as idempotent or documented as at-least-once; do not claim remote exactly once. Allocate any acknowledgement-ledger migration through the orchestrator. Keep existing Digest status values and public API, and do not introduce a queue framework or multiprocess worker claim.

Acceptance for that PR: each injected boundary above leaves a truthful job status and locally retryable content; a completed edition has matching article rows/file and consumes its media; failed publication does not consume media or set seen rows; source acknowledgement failures remain durably pending and later retry without rebuilding an edition; a logging error after commit cannot change a completed Digest to failed; cancellation/restart does not turn an already locally committed edition into a false failure. Test both no-effect and applied-then-error remote outcomes with synthetic mocks, including a crash after provider success but before local ack completion, and state the at-least-once limitation. Do not implement this while bindery and media ownership is split across INGEST-01 and RETENTION-02; rebase and coordinate file ownership first.

The narrow existing data repair question is separate: old failed digests may already own consumed media or remotely acknowledged entries. The follow-up must not silently unconsume or delete those historical records. A conservative one-time audit/report can identify them for operator review; any automated backfill or deletion needs the retention decision.
