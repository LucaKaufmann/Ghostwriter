The next sync still uses the saved instance identity and the existing adapter checks; this change does not bypass validation.

## Independent review correction: resolution during a pending URL edit

Independent review found that leaving A's binding unsuspended during a temporary B preference could let local resolution actions consume A's proposals before sync selected B. `FeedSyncService` now captures the feed binding generation before its asynchronous settings read, then checks the current normalized preference against the persisted destination, generation and suspension before calling the existing resolver. The synchronous check and resolution run in one MainActor turn. `SettingsRepository` writes the persisted generation and UserDefaults preference in one MainActor turn as well; a delayed read cannot use a stale A URL after B is saved. The feed store still owns new-scope suspension when sync selects B, and its original conflict/previous-scope guards remain active. No SwiftData schema, UserDefaults shadow state or server behavior changed.

Real-service App tests prove Keep Server, rejected Discard and previous-proposal Transfer cannot consume or move A's operations while B is configured; reverting to A permits the valid actions. They also preserve a preexisting integrity suspension and hold a URL read while B is saved, then return stale A to verify the generation guard rejects it.
