## Review correction: unusable completed digest

When reconciliation fails a running local run because its referenced digest lacks an EPUB, the expected article associations, or a delivered claim, it now also marks that local digest incomplete. Its diagnostic, history row, existing file, associations, and claim remain in place; no remote digest is changed. This removes false period coverage while retaining the original attempt in the journal, so only the one remaining automatic retry can be admitted. A provably usable committed digest remains complete and continues to cover its period.

## Final review: coverage context and deliver-once boundary

The claim that a preloaded app `ModelContext` blocks the retry did not reproduce. A V3 simulator regression loaded the digest into the same long-lived `DigestRepository` context used by the scheduler before reconciliation, then reconciled through `DeliveryStore`'s separate context. The repository's subsequent date query returned that exact row with `isComplete == false`, and `LocalDigestScheduler.hasDigestCoveringLatestPeriod` returned false. Both launch catch-up and overnight generation use this repository query inside the generation lease. No speculative context reset or scheduler product change was made.

The missing-EPUB/delivered-claim case is a deliberate deliver-once limit, not an automatic restoration guarantee. A real `DigestGenerator` fixture confirmed that reconciliation admits the remaining scheduled attempt but preserves the delivered claim. With no new articles, that attempt ends `empty`, covers the occurrence, leaves the original EPUB missing, and makes no second article-processing call. Explicit `.regenerate` can create a new EPUB and process that article again; it leaves the first delivery claim attached to its original digest. Automatically releasing claims or repeating paid work after file loss would violate the deliver-once policy. The retained history and diagnostic expose the missing artifact, but automatic catch-up cannot reconstruct it without explicit regeneration.

This follow-up changed tests and this result only. The complete Data suite passed **59/59** and `LocalDigestSchedulerTests` passed **9/9** on the V3 iOS 18.6 simulator. SwiftData emitted the same non-failing model-checksum diagnostics as in prior runs.
