# Native feed sync v2: migration and persistence handoff

Prepared read-only on 2026-09-27 from integration `ec340d5`, `docs/contracts/feed-sync-and-local-delivery.md`, `docs/work-packages/mobile.md`, and `sync-kmp-handoff.md`. This is a proposed implementation plan, not a build/test/PR claim. Pin the server and KMP verified SHAs before dispatch. Preserve the contract's exact URL identity, four synced fields, version/instance checks, server-wins-visible plus retained local proposal, and synthetic exclusion. Both native stages use only synthetic fixtures; no provider or production-content access.

## Stage and file ownership

Root owns common contract, schema allocations, shared plan, and integration fixtures. KMP owns only `shared/.../ghostwriter/*V2*`, v2 transport/use case/ports and common tests. Native owners must not modify those ports unilaterally; report the concrete amendments below before KMP freezes.

* **Android, one owner:** `app/src/main/java/com/example/epilogue/data/local/{EpilogueDatabase,FeedEntity,FeedDao,FeedMutationEntity,FeedMutationDao,FeedSyncStateEntity,FeedSyncStateDao}.kt`, `di/DatabaseModule.kt`, `data/repository/{FeedRepository,GhostwriterRepository,SettingsRepository}.kt`, `sync/AndroidSyncAdapters.kt`, `service/FeedSyncWorker.kt`, `ui/feed/{FeedViewModel,FeedListScreen or existing feed view}.kt`, `ui/settings/SettingsViewModel.kt`, focused Android repository/migration/worker/UI tests. `SettingsViewModel` is included deliberately: it has direct bulk calls at ~218 and ~1562 and prior ANDROID-OBSERVE lifecycle edits to preserve. The later ANDROID-DELIVERY owner takes `EpilogueDatabase`/`DatabaseModule` only after Room9 lands, for reserved Room9→10.
* **iOS, one owner:** Domain `Models/{Feed,FeedMutation,FeedSyncState}.swift`, `Protocols/FeedRepositoryProtocol.swift`, `Persistence/{EpilogueSchemaV1,EpilogueSchemaV2,EpilogueMigrationPlan}.swift`; Data `Persistence/PersistenceController.swift`, `Repositories/FeedRepository.swift`; App `Services/{SharedSyncUseCaseFactory,FeedSyncService,GhostwriterSyncCoordinator}.swift`, `Views/FeedListView.swift`, and scoped tests. Own the native `GhostwriterClient` feed write wrapper only if needed to disable/route bypass calls; KMP transport remains the v2 writer. The later IOS-DELIVERY owner appends V3 to this plan and owns `ArticleDelivery`/generation files after iOS sync/delete lands. A test-target manifest edit goes through root/toolchain ownership if required.
* **Delete stage:** implement delete intent in the Room9/V2 schema from day one; a subsequent Android/iOS delete PR can complete UI/replay tests without allocating Room10/V3. Do not overlap platform feed repository edits with delivery or status workers.

## Android Room8→9

Current `EpilogueDatabase` is v8 with schema export disabled; `DatabaseModule` explicitly registers 1→8 migrations and has no destructive fallback. Define `MIGRATION_8_9`, register it, and update entities and DAOs together. Add nullable `serverId`, `serverVersion`, `mutationRevision INTEGER NOT NULL DEFAULT 0` to `feeds`; retain `locallyModified` and `serverUpdatedAt` for compatibility but never use them as v2 authority. Add a durable `feed_mutations` table with exact op UUID, exact URL, binding scope, kind, nullable base, dirty-fields JSON, local revision, monotonic sequence, state, immutable sent payload/flag, server snapshot, safe rejection code/message, and creation time. Add a singleton `feed_sync_state` storing normalized destination URL, configuration UUID, server instance UUID, cursor, first-reconciliation-complete flag, suspended/changed state, and a persisted sequence allocator. The accepted contract's unique `(serverKey,url,sequence)` needs special handling for null unbound keys: SQLite permits duplicate nulls in unique indexes. Use a nonnull scope sentinel/internal key or an expression index, while retaining the protocol's logical null `serverKey` for never-configured intents. Migration creates no automatic uploads. Preserve every old feed row, including `locallyModified=false`, as a full four-field legacy proposal (either staged rows in `feed_mutations` with `needs_reconciliation`, or a separate proposal JSON column/table); leave serverVersion null. Preserve `lastFetched`, digests, history, settings, and synthetic rows. Synthetic rows never enter proposal/outbox/v2 pulls. Capture full values **before** any pull can overwrite the feed row. Use migration SQL within Room's upgrade transaction and verify Room's expected table/index schema, including enum converter representation.

All v2 feed edits go through one repository transaction (`RoomDatabase.withTransaction`): validate exact URL/fields, read binding/current server snapshot and per-URL head, increment `mutationRevision` and persisted sequence, update visible feed fields (or hidden-delete state), append a new op ID and dirty fields, then commit. Old `FeedViewModel` plain insert/update/delete must call this method; `FeedDao.deleteFeed`/`REPLACE` are server-import-only internals. Do not physically delete a locally deleted feed while a pending delete or conflict needs its URL, server ID/version, and proposal. Exclude hidden deletes and ambiguous pre-upgrade tombstone/absence from normal list and generation queries. A local-only edit still persists an unbound intent without network work. URL change is ordered delete old URL plus create new URL, never in-place key replacement.

First successful **complete** v2 pull transactionally compares every legacy proposal to exact-URL server active rows/tombstones/absence, stores the latest server snapshot separately, binds destination/config/instance and cursor, then marks first reconciliation complete. Exact four-field matches adopt server ID/version; differences and tombstone/absence become `needs_resolution`, retain local proposal, and cannot auto-send. Absence offers Keep removed/Add to server because old tombstone purge makes history unknowable. Genuinely post-upgrade unbound creates/deletes are distinguishable from legacy proposals: never-seen creates may use null base; existing/tombstoned URL or unbound delete of existing remote state requires explicit resolution. No partial/failed full pull can mark binding complete. A later destination/config UUID change suspends old binding and intents; disabling integration retains it. Credentials alone do not change identity. Keep binding, config UUID and outbox in Room, not split between Room and `SettingsRepository` SharedPreferences; read the current URL/flag from settings, compare under the sync gate, and persist/validate a destination-generation token before each native commit/network send to close settings-change races. The settings writer must suspend the old binding before triggering initial sync. Do not reinterpret a completed binding as first setup.

`loadPendingMutations` transactionally claims at most one eligible head per exact URL and at most 100 URLs, marks first send, and returns frozen op/base/fields/revision. A run gate (shared between WorkManager and manual/settings invocations) prevents concurrent same-URL sends; after process death resend the identical frozen payload and op ID. Edits during flight append a successor. Delete then re-add remain two ordered rows, with re-add blocked until delete acknowledgement and rebased on its tombstone version. For an accepted result, transactionally remove only the matching op ID + sent revision; do not clear all dirty flags. Apply `current` only if its version is at least the stored snapshot; stale receipt still acknowledges its exact row and forces a pull. A conflict/rejection saves current row and proposal, blocks later same-URL ops; rejection stores safe code/message and stops automatic retry. Pull applies rows in ascending version with cursor in the same Room transaction; failure rolls both back. A pull never overwrites a pending proposal/hidden delete. Last-success timestamp changes only for a truly complete outcome.

## SwiftData current unversioned→captured V1→V2

The production container currently opens `Schema([Feed, Digest, DigestArticle])` directly, with `Feed.url` unique and no `VersionedSchema`/`SchemaMigrationPlan`. Capture the **exact deployed shape** as `EpilogueSchemaV1`: the old Feed properties (including createdAt, serverUpdatedAt, locallyModified), Digest, DigestArticle and relationships/unique attributes must retain their persistent names. Introduce V2 with optional `serverId`/`serverVersion`, `mutationRevision=0`, and persisted `FeedMutation`/`FeedSyncState`; keep existing public `Feed` call sites source-compatible using a V2 model alias or a deliberately narrow migration of references. Register `[V1,V2]` and a V1→V2 stage in `EpilogueMigrationPlan`, open the same on-disk URL/configuration through `PersistenceController` with `migrationPlan`, and fail visibly on migration error. Do not delete/recreate the store or silently switch to an empty URL. The decisive test must create a database using the **current unversioned app schema**, close it, and reopen it with the new V2 container; creating a fresh V1 test store alone does not prove installed-store migration. If SwiftData cannot recognize the unversioned store as captured V1, stop and demonstrate a supported bridge/explicit backup-and-import before shipping. Also prove a V2 store opens again after app restart. V3 delivery is appended later, never mixed into this stage.

Migration/save must preserve all old feeds and their full four-field proposals independent of `locallyModified`, plus all digests/associations. As on Android, matching remote rows adopt version; mismatch/tombstone/absence persist both snapshot and proposal with explicit resolution. Persist destination/config/instance/cursor/first-binding marker in the same SwiftData store as mutations, not only SettingsRepository/UserDefaults. Use a single `ModelContext` per semantic operation, insert/update all participating models and save once; verify rollback behavior on injected save failure and reopen after a process/session boundary. Prevent context autosave of a changed `Feed` before its outbox row is created: feed UI must call repository semantic methods and avoid mutating `@Model` properties directly from view state. A hidden-delete/tombstone state must survive without hard-deleting its only feed row; generation fetches filter it. Guard `@Attribute(.unique)` upserts from silently replacing an existing keyed feed. Allocate persisted per-scope/per-URL sequence transactionally and serialize concurrent `ModelContext` writers through an actor/main-actor gate; SwiftData's save alone does not prove cross-context compare-and-swap. `FeedMutation` stores immutable sent payload separately from newer editable proposal; `FeedSyncState` stores binding and counter. If SwiftData cannot atomically enforce identity/sequence/claim across contexts, use a dedicated serial persistence actor/journal and prove restart behavior before claiming v2 durability.

## Bypasses and UI minimum

Android `FeedSyncWorker`/`AndroidSyncAdapters` currently invoke v1 KMP. `GhostwriterRepository.syncFeeds` has both shared-client and legacy Retrofit branches and converts 0→10; `SettingsViewModel.runDigestViaGhostwriter` and `performInitialGhostwriterSync` invoke that full-list method directly. `FeedViewModel` plain writes and direct `deleteFeedByUrl` bypass an outbox. Route all these feed operations through the same v2 repository/use case; a server-generation action may proceed only with an explicit partial/upgrade state when feed sync is incomplete, not report “feeds synced.” Preserve the already-enabled hidden Ghostwriter flag and both settings client flag modes, but neither may choose a v1 writer. Keep unrelated config/schedule/digest APIs.

iOS `FeedSyncService.sync` uses the old shared bridge; `pushLocalFeeds` calls native `GhostwriterClient.syncFeeds` and converts 0→10; `notifyFeedDeleted` calls native unversioned DELETE. `GhostwriterSyncCoordinator` runs that push with heartbeat and later applies feed data from combined `/sync`; both normal and forced paths can overwrite v2 state, and fallback invokes the old bridge. `FeedListView` add/edit/delete mutates SwiftData directly with `try?`. Replace these paths with semantic repository methods and one v2 feed sync entry; combined sync may continue for config/digests/schedules but must ignore its feed section and never clear v2 flags/cursor. All actual feed failures, partial/conflict/rejected/upgrade/changed-instance outcomes remain visible and cannot become generic lastSyncTime success. Preserve offline local reading and existing feature-flag behavior.

Both clients need a feed-list/settings badge or row for `needs_resolution` and `rejected`, showing latest server values, retained local dirty fields, and safe error. Actions: Keep server/Apply mine for edit conflict; Keep feed/Delete anyway for delete conflict; Keep removed/Add to server for legacy absence; Correct/Discard for terminal rejection. Correction uses a fresh op UUID and current server base after refresh. Discard removes only the selected proposal; dependent successors stay blocked and require fresh explicit resolution (optional discard-all must show what is lost). Never erase an unresolved proposal on pull or by editing another field. A `ServerUpgradeRequired` or `ServerChanged` state is visible; old-server preview is read-only and never advances v2 state.

## Shared-port amendments to settle before KMP starts

1. `FeedV2StorePort.reconcileAndBindFullSnapshot` needs to distinguish a **complete** first pull and legacy pre-upgrade proposals from truly post-upgrade unbound intents. Specify persisted origin/state in the native store contract; `locallyModified` is insufficient. Ensure `FeedSyncV2UseCase` cannot call reconciliation with an incremental response or a partial page.
2. Add `suspendBinding(expectedBinding, reason: ChangedDestination|ChangedInstance): FeedV2StoreResult` as an atomic native operation that marks the old cursor/outbox non-sendable. Returning `ServerChanged` alone leaves them eligible to a concurrent manual run. Every store operation must check a persisted binding/destination generation token. A 409 or HTTP200 instance mismatch invokes suspension before the run ends.
3. Add bridge-friendly `beginSyncRun(destination): RunToken?` / `endSyncRun(token)` on the native singleton store, with a process-local exclusive gate spanning network I/O; all mutating port calls take/check token and persisted destination generation. Android WorkManager/manual/settings and iOS coordinator/manual calls must use the same singleton. On process death the gate vanishes but a sent row's frozen payload/op ID remains, so replay is safe. A durable lease is necessary only if a second sync process is actually introduced. Make `loadPendingMutations` return typed claimed/empty/stale-binding/storage-failure instead of treating a failed load as no work. Add `pendingSummary(expectedBinding): FeedV2WorkSummary` with eligible, blocked-conflict, rejected, and unsent successor counts plus typed error, so `Complete` cannot be inferred from an empty batch. One head per URL is essential; `acknowledge` and pull likewise cannot report complete while work is blocked.
4. Define a native resolve API/semantic transaction for Apply mine, Keep server, Correct, Discard, and delete/re-add successor blocking. The current proposed port covers remote results only; a UI cannot safely edit rows ad hoc while KMP sync is active.
5. Clarify whole-batch validation before any per-result acknowledgement: exact instance, exactly one result per sent op, no extras, valid row kind/URL/version. `applied current:null` is valid only for never-seen delete; older receipt current cannot roll visible state backward. KMP must propagate typed invalid-response/partial states without a v1 fallback.
6. Make settings/config scope identity explicit: normalized destination URL + persisted configuration UUID + observed server instance, with credentials-only changes preserving binding. Both native stores need a transactional local sequence allocator; `(NULL,url,sequence)` uniqueness is not enforced by ordinary SQLite UNIQUE.

## Acceptance and exact verification gate

Use the verified native baseline/toolchain from BUILD-NATIVE. Android: generate a real v8 on-disk fixture with existing feeds (dirty true **and false**), synthetic, digest/history/settings; upgrade via Room 8→9 migration under `MigrationTestHelper` or equivalent, inspect rows/indices, reopen v9, and run repository transaction tests with injected failure/restart. Run `./gradlew :app:testDebugUnitTest :shared:testDebugUnitTest --no-daemon` and `./gradlew assembleDebug --no-daemon`; on-device/instrumented migration if the host supports it. iOS: create an actual old unversioned SwiftData store at a temporary URL, reopen via V1→V2 plan, assert all rows and proposal values, restart/reopen and inject save failure; run fresh shared XCFramework build, `tuist install && tuist generate`, then the Data, Domain, GhostwriterClient and App test schemes and simulator app build with signing disabled. Capture exact xcodebuild commands/destinations and results in stage result files. Generated project files are not source edits.

Required persistence fixtures on **each** platform: pre-upgrade dirtyfalse mismatch/match/tombstone/absence; synthetic exclusion; full-pull failure never binds; offline edit/delete then process restart; local-only and server URL/config switch; same-URL replacement instance on HTTP200 and 409; unchanged client sees web version5; two clients conflict at base4; unrelated-field web change conflicts; timeout replays identical sent op; edit during flight keeps successor; delete then re-add order/stable UUID; accepted older receipt after newer pull; missing/duplicate/extra result keeps all intents; rejected op correction/discard with blocked successors; pull apply failure leaves cursor; successful pull after failed push stays partial; `maxArticles=0` transmitted unchanged. Test both Android shared and legacy setting, normal/forced iOS combined and fallback paths, and assert **no** `/feeds/sync` or unversioned feed DELETE/PUT call from a v2 client even on 404/405/auth/transport failure. UI evidence must show conflict actions and upgrade/changed states. Root's combined fixture uses server v2 + web + Android/iOS stores; individual green suites alone are insufficient.

Material limits at this preparation point: no implementation or runtime validation was performed; server review is still pending, and the KMP port amendment list is an integration gate. SwiftData unversioned-store recognition and cross-context transaction behavior require executable fixtures before the iOS plan can be called safe. This plan does not cover Room10/V3 delivery implementation, though it preserves their reserved migration order.
