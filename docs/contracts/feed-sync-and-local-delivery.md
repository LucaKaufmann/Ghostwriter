# Feed sync and native local delivery contract

Status: accepted implementation contract, 2026-09-27; originally based on e6e62677fe4f5b8f516e226a48080008cafc04e0. The implementation checkpoint below and project-state verification supersede historical source observations. Product decisions confirmed by the owner: preserve newer server state and retain conflicting local edits; deliver once in normal local editions, including after history deletion; allow explicit regeneration. The orchestrator owns the protocol, schema reservations, and sequential integration below. No product implementation is claimed by this document. Applies to Ghostwriter feed configuration and native, locally generated EPUBs; Ghostwriter server article dedup is a separate ledger.

## 1. Feed identity, protocol, and conflict policy

The feed key is the **exact stored URL string**, as today (`feeds.url` unique; native `Feed.url` unique). Do not silently canonicalize existing keys. URL editing is delete plus add. The server's UUID is a stable identity for that key, including soft deletion and restoration. Native stores it when known; an older local feed can resolve it from a full pull by exact URL. Synthetic URLs never enter this protocol. Exclude persisted `synthetic://*` rows from both full/incremental changes and client mutations. Their internal creation keeps version0 and does not consume the external feed clock; version backfill skips them. The legacy source helper may continue to create those internal rows without passing through the public feed mutation API. The four synced fields are `title`, `is_active`, `mode` (`raw`/`summarize`), and `max_articles`; `lastFetched`, local creation time, and delivery state are local only. Preserve native `maxArticles=0` as unlimited and transmit `0` in v2; the server must accept and retain it. Server ingestion must interpret zero as no per-feed cap, while preserving existing global generation limits. The audited `entries[:0]` bug was corrected by the server stage; synced zero-limit feeds have end-to-end fixture coverage. Negative limits are rejected. The old v1 client maps `0` to `10` and must never write that value over an existing feed.

`version` below is a server-assigned, monotonically increasing **global feed change sequence** (`int64`), not `updated_at`. Every server create, actual edit, delete, or restore gets a new sequence in the same DB transaction. `version` on a feed is its latest sequence. Pull cursor is the last fully applied sequence. Server timestamps remain display/legacy fields; no clock comparison decides conflicts. Every web write and native mutation must pass through the same version-allocation path. Read-only/no-op requests do not advance it.

Add `GET /feeds/changes-v2?since_version=<int64>&server_instance_id=<bound UUID>`; the instance parameter is omitted only on first binding/reconciliation and mismatch returns409 before reading changes; no cursor means complete non-tombstoned feed list (including `is_active=false`) **and tombstones**, with `server_version` high-water mark. Subsequent calls return rows where `version > since_version`; each row is either an active `feed` or tombstone, carries `id,url,version`, and is ordered by `version` ascending. Both pull and mutation responses include persisted server-owned `server_instance_id` (UUID); every mutation request supplies the instance ID last observed on pull. A mismatch returns HTTP409 `server_changed` before any writes. A fresh database gets a new ID. A database restore workflow must rotate the ID before serving writes, even when restoring its previous ID from backup; The server stage must ship the restore-identity rotation command and update `ghostwriter/RELEASE.md` backup/restore procedure before enabling v2 writes. Its fixture must restore a pre-mutation database, rotate identity using that command, then prove an old-instance mutation is rejected without writes. This is a rollout prerequisite in the server PR, not deferred work; RELEASE-01 later repeats the integrated readiness check. Do not enable v2 writes or authorize deployment without this evidence. A cursor greater than current high-water also returns `server_changed`. Before applying any successful pull or mutation response, clients compare its instance ID with the persisted binding; a mismatch is `server_changed` even for HTTP200, and no rows, acknowledgements or cursor changes may apply. Clients suspend old bound outbox/cursor on either signal and require explicit reconciliation; they must not silently replay against a replacement. The server returns a consistent snapshot up to `server_version`; do not advance the client's cursor beyond a failed local apply. Tombstones must be retained for the supported lifetime of sync clients; do not purge them as part of digest cleanup. If records can be purged in future, add an explicit `cursor_expired` response and force a full reconciliation rather than treating missing rows as deletes.

Example pull:

```json
{"server_instance_id":"21410e08-44a1-4944-8910-5a74c39a7271","server_version":42,"changes":[{"kind":"feed","id":"2df6a71e-2db3-428b-8372-058794b8df35","url":"https://example.test/rss","version":41,"title":"New title","is_active":true,"mode":"raw","max_articles":0},{"kind":"tombstone","id":"92ae12f1-ac87-4b56-a86f-9e7607b38462","url":"https://example.test/old","version":42}]}
```

Add `POST /feeds/mutations-v2` with `mutations` array. Each mutation has UUID `op_id` (stable across retries), `url`, `kind: upsert|delete`, `base_version: int64|null`, and, for upsert, a `fields` object containing **only dirty synced fields**. `base_version=null` means create a URL that has never existed on this server; it never means overwrite current state. Partial fields avoid overwriting unrelated web edits. Deletes carry no fields. Each item is independently transactional; the server returns one outcome per item in request order. One failed/conflicting item does not roll back accepted siblings. The HTTP request is `200` for a syntactically valid batch, including mixed outcomes; malformed envelopes/auth fail at HTTP level with no mutation. The maximum batch is 100 items: missing/non-array/oversized envelopes or duplicate op IDs return HTTP 422 before writes. Each item with a valid UUID receives its own result; malformed item op IDs are an envelope error because results cannot be correlated. Other field validation errors are `rejected` per item. Versions are nonnegative integer JSON numbers bounded by 2^53-1, stored as int64 in the database/KMP. If the clock is exhausted, reject further writes without mutation; never wrap or round. The bound preserves exact first-party web comparisons. New upserts require all four synced fields; existing upserts allow a nonempty subset, rejecting unknown keys. `title` is a nonnull string (empty remains allowed for compatibility), `is_active` is a Boolean, `mode` is raw/summarize, and `max_articles` is an integer from0 through2147483647 (signed32bit, matching Kotlin Int and the iOS Int32 bridge);0 remains unlimited. Web/legacy request validation and v2 per-item validation reject values outside that range before writing.

```json
{"server_instance_id":"21410e08-44a1-4944-8910-5a74c39a7271","mutations":[{"op_id":"3e1a59a5-f547-40b2-9a6b-4c54e80a03dc","kind":"upsert","url":"https://example.test/rss","base_version":39,"fields":{"title":"My title"}},{"op_id":"a61d59d1-d936-4cfb-a20e-97718ddb0ff2","kind":"delete","url":"https://example.test/old","base_version":37}]}
```

```json
{"server_instance_id":"21410e08-44a1-4944-8910-5a74c39a7271","results":[{"op_id":"3e1a59a5-f547-40b2-9a6b-4c54e80a03dc","status":"conflict","current":{"kind":"feed","id":"2df6a71e-2db3-428b-8372-058794b8df35","url":"https://example.test/rss","version":41,"title":"Web title","is_active":true,"mode":"raw","max_articles":0}},{"op_id":"a61d59d1-d936-4cfb-a20e-97718ddb0ff2","status":"applied","current":{"kind":"tombstone","id":"92ae12f1-ac87-4b56-a86f-9e7607b38462","url":"https://example.test/old","version":43}}]}
```

`applied` includes an idempotent replay of the **same** `op_id` and payload. An `op_id` reused with different payload returns `rejected/op_id_reused`; receipts survive server restart. `conflict` includes the current row or tombstone; it does not apply any local fields. `rejected` includes stable `code` (`invalid_url`, `invalid_fields`, `unknown_base`, `op_id_reused`) and safe message. A delete for a URL that never existed is `applied` with `current:null` and a durable receipt; an upsert with null base against an existing or tombstoned URL conflicts. A delete replay against an already deleted row with a *different* `op_id` conflicts unless its supplied base matches the tombstone's current version, in which case it is an acknowledged no-op. Network failure or a missing/duplicate/unrecognized result is unknown, so retain and retry the same `op_id`. Receipts store the original terminal outcome in the same transaction as the mutation; replay returns it. A receipt snapshot may be older than the latest pull: apply a server snapshot only if its version is at least the locally stored server version. Acknowledging an older applied op still removes only that exact proposal and schedules a pull; it never rolls visible state backwards. Transient server/storage failure is not a terminal receipt. A terminal rejected result persists `state=rejected` with its code/message and original proposal, stops automatic retries and blocks later operations for that URL. The conflict screen offers Correct or Discard. Correct edits a preserved proposal after refreshing current server state and replaces the rejected row with a new UUID, fresh base and unsent payload in the same local transaction; never reuse the rejected op ID. Successors remain queued and ordered, rebasing only after the replacement applies. A URL correction is a new URL-keyed intent; do not change the rejected row's identity in place. Discard removes only that rejected proposal; before releasing successors require refreshed explicit resolution where their assumed predecessor/base no longer holds. A reused-op-ID error is also terminal and cannot be fixed by blind automatic retries. Rejected mutations contribute partial/failed sync status and are visible until resolved.

For a stale baseline, **any** intervening version change conflicts even if dirty fields differ. This conservative choice prevents hidden interaction with deletion and re-add. The newer server row wins the visible synced state; the local proposed values remain in a durable conflict record until the user resolves them. Expose a conflict action in both clients (feed settings/list is sufficient): **Keep server** discards only that pending mutation; successors whose proposed state assumed that predecessor remain blocked and marked `needs_resolution` against the fresh server snapshot, never automatically rebased/sent. The UI may offer an explicit discard-all-proposals action after showing what will be lost; **Apply mine** creates a new mutation with the current server version and the preserved dirty fields. A delete conflict offers **Keep feed** or **Delete anyway**. No automatic last-arrival overwrite. Applying a new local edit while a conflict exists updates the proposed field set, never silently clears it. Local-only metadata remains local.

Client push order: mutations become immutable before their first send, including their op ID, base, payload and revision. A timeout does not make an operation editable again. New edits receive a new op ID and monotonically increasing per-server/per-URL local sequence; timestamps are display metadata and never order operations. At most one op for a URL is in flight; independent URLs may share a batch. Unsent queued successors may be compacted/rebased, but a sent operation must replay identical canonical JSON payload (object key ordering is irrelevant). Persist mutation and increment local `mutation_revision` atomically with each local edit; snapshot `op_id`, `base_version`, fields, and revision for the request. Apply per-item acknowledgements to the matching outbox row only when `op_id` and that row's sent revision match; a newer feed revision does not prevent acknowledging an older immutable row. If a user edits during flight, keep the newer mutation pending; after an accepted older mutation, rebase its unsent successor on the returned server version (unless a newer pulled version is already known, in which case require conflict resolution instead of assuming it was observed by that edit). On conflict, save the server snapshot and proposed fields, mark `needs_resolution`; a pull may update the server snapshot but cannot erase the proposal. Pull applies each row transactionally with cursor progress and must not overwrite pending fields/delete intent. Sync outcome is `success` only if all requested pushes and pull apply succeeded with no unresolved conflict; mixed accepted+conflict/failure is `partial` with counts and pending intent; transport/auth/pull-apply failure is `failed` for that phase, without claiming a new cursor or generic last-success timestamp. A successful pull after failed push is still partial.

Local delete first writes a durable delete intent and hides the feed from normal UI/generation in one transaction. It remains across offline/restart, even when a full pull includes that feed. Replay with its original `op_id` and base. Clear it only on per-item `applied` response (or explicitly resolved conflict). On conflict with a server edit or restore, keep the feed hidden and show the server snapshot until resolution. A local re-add of the same URL after a pending delete is **ordered after** that delete: preserve both operations in a per-URL queue, apply delete first, then re-add using the acknowledged tombstone version. If the delete conflicts, block the later re-add pending resolution. Server re-add/restore from another device obtains a newer version and therefore conflicts with a stale delete. Bind pending outbox rows to the configured Ghostwriter server identity (normalized base URL plus a locally stored configuration UUID and the server-owned instance UUID); changing destination suspends old intents and requires explicit migration/discard, never sends them to a different server. Local-only mode keeps intents without network attempts. Before any server has been configured, outbox `serverKey` is null (unbound). First configuration/pull atomically associates those rows with the observed binding without changing their proposed values, using null base because they have no server baseline. Never-seen upserts may create; same-URL existing rows/tombstones become conflicts. An unbound delete cannot delete an existing remote feed: it also requires explicit conflict resolution; a never-seen delete is an acknowledged no-op. Persist completed binding so a later destination change cannot be mistaken for first setup. Once bound, disabling integration retains the same binding and resume behavior.

A saved server-URL edit invalidates in-flight work without discarding the original binding or proposals. Conflict actions verify the currently saved destination. Reverting a temporary edit before sync selects a different destination may resume the original binding; it never clears a preexisting integrity suspension or a suspension after actual selection of a different server. Persist sync outcomes only for the binding and generation actually used by that run, or the current disabled observation for `NotConfigured`, so old results cannot overwrite current status.

### v1 and rollout safety

The existing `/feeds/sync` posts full snapshots and presently overwrites changed server fields; change it on v2 server rollout to allow exact no-ops only, but return `409 legacy_write_requires_upgrade` for **any create, changed existing or tombstoned URL**, with no partial batch writes. Existing `PUT /feeds/{id}`, both DELETE routes, and `POST /feeds` when it would restore a tombstone require `If-Match: "<decimal version>"` on v2 server and return `428` without it, `409` with a stale version; update the first-party web UI in the server stage to read/send the version, retain the edit form on 409, and offer refresh/retry against the new server snapshot. Creating a never-seen URL remains possible without a version. A create call encountering a tombstone returns 428 with its safe current snapshot so the web can explicitly restore using the version; it cannot silently overwrite it. Never accept an unversioned restore from v1 sync or another importer. Do not expose deleted feeds through ordinary active lists. This is an intentional restriction on old-client edits/deletes so old binaries cannot undo newer server data. Legacy GET/list/changes, combined sync, and response fields remain available; extra `version` field is additive. Old clients may still read. Legacy bulk creates are rejected because a missing URL may have been deliberately deleted and purged by a pre-v2 server; no retained evidence can distinguish that from a new client source. Only the explicit versioned create flow (or first-party user create request) can create it. This compatibility limit must be shown as upgrade-required by updated clients and documented for older binaries. New clients probe v2 at configuration/sync time; if it returns 404/405 (older server), display `server_upgrade_required` and provide a required native read-only preview that fetches the legacy feed list on explicit user request. Keep all pending edits/deletes. The shared v2 use case returns the typed upgrade outcome; the platform compatibility view owns the legacy GET. Preview rows do not enter the versioned local feed store, cursor, binding or outbox because an unversioned response cannot establish the required conflict baseline. This preserves access to older-server feeds without treating preview as successful synchronization. Never fall back to v1 write or clear pending state. A downgraded client against the v2 server is read-safe and cannot modify existing feed configuration through unversioned routes. Rolling the **server binary** back against a v2 database is unsupported and prohibited: old write handlers lack guards and its background tombstone cleanup can erase sync history even if ingress blocks writes. Keep that database on v2; never give an older binary write access to it or run its maintenance jobs. Any separately planned rollback must use an isolated pre-v2 backup with client reconciliation and the required identity rotation before later v2 writes; blocking ingress alone is not a rollback strategy.

## 2. Native local delivery

Normal local generation is incremental by durable **article identity**, independent of publication date and digest history. Key is `(feed_url, article_key)` where `article_key` is `SHA-256` of a shared URL normalization: parse absolute HTTP(S) article link, lowercase scheme/host, remove default port and fragment, retain path, query and non-default port exactly (including query ordering and percent escapes), preserve path case; canonicalize an empty path to `/`, serialize IPv6 hosts with brackets, reject user-info, and include shared fixture vectors so Kotlin and Swift hash the same UTF-8 string; no title/date fallback. A malformed/missing link is `invalid_identity` and remains undelivered. Duplicate normalized links within a feed are one candidate, even if distinct feed entries have different dates; different feeds can deliver the same link independently. `publishedAt` is only display/order metadata, never a delivery cursor. Older `lastFetched` can remain for compatibility/UI but must not filter normal candidates after the delivery ledger is active. Parse the entire feed page made available by the parser; select **undelivered** candidates first, ordered by least recently attempted (never attempted first, original feed order as tie-breaker), then take per-feed `maxArticles` (`0` unlimited). Persist an attempt sequence for selected identities before processing: a failed/cancelled item remains eligible but moves behind not-yet-attempted deferred items on the next normal run. This guarantees progress across a finite feed window even if its earliest entries always fail; publication order is preserved within equal attempt age. Explicit regeneration uses the same fair attempt ordering so capped repeats reach later items. Attempt bookkeeping never means delivered or excluded. Do not count cap overflow as delivered or permanently advance past it. If a parser enforces an upstream cap, that cap must be exposed as truncation/partial and pagination added or the implementation cannot claim overflow recovery.

All local manual/scheduled/worker generation entry points on a platform share one generation coordinator, so a second normal run does not concurrently select or pay to process the same identities. At finalization the DB transaction also atomically claims every normal-delivery identity using a state-aware compare-and-set in the same write transaction: insert delivered when no row exists, or change retryable to delivered; an excluded row may transition only when the stored filter signature differs from the current one or the run explicitly regenerates. A pre-existing retryable/eligible-excluded row is not a duplicate-delivery conflict. If any selected normal-run identity was already delivered by another run, roll back the entire losing digest/history/ledger transaction, remove only its own unique artifact, and return a retryable conflict diagnostic. Never commit a duplicate digest merely because ledger insertion ignored a uniqueness conflict. Excluded-to-delivered transitions require the matching filter signature/re-evaluation rule. Explicit regeneration remains serialized for artifact safety but may intentionally repeat delivered identities. Cancellation releases the in-memory gate; process restart clears it naturally. Include Android worker/manual and iOS LocalDigestService/LocalDigestScheduler entry points in platform delivery ownership.

State for each eligible item: `unseen/retryable → processing → delivered`, with `processing` transient/in-memory and never a durable exclusion. The ledger permits durable `retryable` rows solely for fair attempt ordering; they are always eligible and have no firstDigestId. `lastAttemptSequence` is a monotonic local integer allocated from persisted generation-run sequence, never a wall-clock exclusion cursor. A completed/failed/cancelled run must not erase this fair-selection marker; none of these markers are terminal delivery claims. `delivered` is inserted only in the same DB transaction that completes a usable digest/history row and its article associations, after EPUB bytes are durably written to a unique path. On EPUB write, history finalize, cancellation, or DB failure, none of those items become delivered; orphan files may be cleaned on retry. On crash after DB commit, the ledger suppresses duplicate work. Deleting old digest history or EPUB does **not** delete delivery ledger rows. Feed removal does not erase ledger for that URL; re-add retains once behavior. Explicit **Regenerate** is a separate invocation that can select previously delivered items and create a new digest; it preserves existing delivered claims (first digest/commit identity), while retryable or excluded rows may transition to delivered under the re-evaluation rule; fair attempt metadata may advance. It does not change normal-run dedup policy. The existing Android `KEY_FETCH_ALL` maps to this explicit invocation only. iOS needs an explicit equivalent UI/service argument, not a silent scheduled mode. Android history clearing must state that delivery claims remain and direct users to explicit Regenerate when repeats are wanted; it must not promise that resetting old feed timestamps changes eligibility.

For each feed fetch, return structured `FeedIngestionResult` with `feed_url`, `candidate_count`, `selected_count`, `delivered_count`, `filtered_count`, `failed_items[{article_key?,url?,stage,code}]`, `cap_deferred_count`, and `feed_error?`; result is not just `[ProcessedArticle]`. A successful parse of an empty feed is `empty`. Fetch/parse exception is `failed` and cannot be converted to empty. Deliberate promotional/short-content rejection is `filtered` with a durable terminal `excluded` identity and a filter reason only after successful result commit; if all candidates are excluded, an atomic empty-result commit may record exclusions without an EPUB. It does not appear in the EPUB and avoids repeated paid processing. Exclusions also store `filter_signature`, a stable hash of the local filter implementation revision plus relevant filtering preferences. A differing signature or explicit regenerate re-evaluates exclusions; delivered rows ignore the signature. An exclusion must never replace an existing delivered row during regeneration; ordinary history deletion does not. Extraction/AI errors are retryable undelivered items. Preserve Android's existing full-article fallback for a transient summary error; if that full article enters a completed EPUB, it is delivered once and the fallback is reported. iOS briefing AI errors remain retryable failures under its current behavior. Cancellation propagates and leaves no terminal identity. Invalid identity can be reported but cannot be ledgered, so it may recur until source correction. Do not equate a parser-rejected item with a successful empty source.

Generation result: `deferred` when no EPUB is produced, every selected candidate was intentionally excluded, no fetch/item/persistence errors occurred, and the cap left other candidates for a future run. Commit exclusions and a persisted run diagnostic with counts in this case, display “No articles included; more remain for the next edition,” and leave deferred identities unseen. Do not report a downloadable digest or failure. `complete` when EPUB/history commit succeeds and all selected eligible items are either delivered or intentionally excluded, with no feed failure or cap deferral; `partial` when a **usable committed EPUB** contains one or more articles but any feed/item fails or cap defers others; `empty` only when all feeds parsed successfully and no eligible candidates remain (including known exclusions), with no cap deferral; `failed` when no usable EPUB exists due to processing, fetch, EPUB, or persistence failure, or when all candidates failed. A cap-limited but otherwise usable EPUB is partial. A `partial` digest carries counts/errors in persisted status or companion diagnostics; do not claim a clean success or hide them. Retry failures and deferred items in future normal runs, without repeating delivered items. A failed feed does not block usable articles from other feeds. No real provider calls in tests.

## 3. Concrete storage amendments and migration boundaries

Server: add `feeds.version BIGINT NOT NULL DEFAULT 0`, backfill each non-synthetic current row with a unique ordered sequence; `synthetic://*` rows remain version0 and consume no sequence; add `feed_sync_clock(id INTEGER PRIMARY KEY CHECK(id=1), version BIGINT NOT NULL, server_instance_id TEXT NOT NULL)` seeded to max and a generated UUID; add `feed_mutation_receipts(op_id TEXT PRIMARY KEY, payload_hash TEXT NOT NULL, result_json TEXT NOT NULL, created_at DATETIME NOT NULL)`; keep existing `feeds.deleted_at` and unique URL. Retain receipts for the supported replay lifetime (no automatic cleanup in this backlog). Serialize the clock allocation and row CAS in a SQLite write transaction; under SQLite use `BEGIN IMMEDIATE` or equivalent to avoid duplicate sequence allocation. The next **root-allocated** Alembic revision must be idempotent, import models in env, and test fresh and previous-revision databases. Do not invent an ID in implementation workers.

Shared ports: replace bulk `syncFeeds`/`clearAllLocallyModified` use in active path with `loadPendingMutations`, `acknowledge(opId, sentRevision, serverRow)`, `recordConflict`, `applyServerChangesAndCursor`, and `getServerIdentity`; expose typed `Complete/Partial/Failed/NotConfigured/ServerUpgradeRequired/ServerChanged` outcome. Implement v2 DTOs above in KMP and native bridges. Keep legacy DTOs only for read compatibility. All feed UI mutations must call an atomic repository method that records dirty fields or delete intent; raw save/delete paths may remain for server import only.

Native delivery also persists `GenerationRun` diagnostics independently of a completed Digest, so excluded-only/deferred/failed runs remain observable without fabricating a downloadable history entry. Reserve Android `GenerationRunEntity.kt`/`GenerationRunDao.kt` in Room10 and iOS `Models/GenerationRun.swift` in V3, alongside each delivery model. Fields: runId, local attempt sequence, startedAt, finishedAt, outcome, optional digestId (no cascade), and structured counts/errors JSON. iOS catch-up also persists trigger and scheduled period on each run, including empty/deferred runs, and treats completed/partial/empty/deferred outcomes as coverage for that occurrence; Android app-launch catch-up must likewise recognize persisted completed/partial/empty/deferred scheduled occurrences; the review follow-up reserves additive Room11 trigger/period/occurrence fields for this, preserving legacy history coverage and leaving unknown old run identities uninferred. Error text must not contain article bodies/credentials.

Android Room (currently v8; root allocates next actual version after integrations): add nullable `serverId`, nullable `serverVersion`, integer `mutationRevision DEFAULT 0` to `feeds`; retain `locallyModified` during transition but derive new pending state from the outbox. Add `feed_mutations(opId TEXT PRIMARY KEY, serverKey TEXT, url TEXT NOT NULL, kind TEXT NOT NULL, baseVersion INTEGER, fieldsJson TEXT NOT NULL, localRevision INTEGER NOT NULL, state TEXT NOT NULL, serverSnapshotJson TEXT, rejectionCode TEXT, rejectionMessage TEXT, createdAt INTEGER NOT NULL, sequence INTEGER NOT NULL, sent INTEGER NOT NULL DEFAULT 0)` with a unique index `(serverKey,url,sequence)`; add sync cursor/server binding in a Room singleton table, updated in the same transaction as feed/outbox reconciliation and cursor application; SharedPreferences must not hold this transactional state. Add `article_delivery(feedUrl TEXT NOT NULL, articleKey TEXT NOT NULL, state TEXT NOT NULL CHECK(state IN ('retryable','delivered','excluded')), reason TEXT, filterSignature TEXT, lastAttemptSequence INTEGER NOT NULL DEFAULT 0, firstDigestId INTEGER, committedAt INTEGER NOT NULL, PRIMARY KEY(feedUrl,articleKey))`; do not cascade from digest. All pre-upgrade local feed rows migrate with `serverVersion=NULL` and a preserved legacy snapshot/proposal, regardless of `locallyModified`: both current UI paths can edit without setting that flag. On initial full v2 reconciliation, a matching server row adopts its version without a write; a differing row/tombstone becomes `needs_resolution`, retaining all local synced fields as the proposal. An absent server URL is also unresolved: older servers may have purged its tombstone after30days, so absence cannot distinguish a never-published local feed from a deleted server feed. Do not auto-upload or silently discard it. Show “Not present on server” with explicit Keep removed (discard proposal/hide) or Add to server (new null-base op) actions. Until resolved, preserve the local snapshot in a pending-conflict view and exclude ambiguous absent/tombstoned feeds from automatic generation. This reconciliation uses a complete successful full snapshot only, never a failed/partial pull; transactionally persist its completion. Genuinely new post-upgrade unbound proposals follow the first-binding rule above. The user chooses Keep server/Apply mine for differences; no pre-upgrade proposal is blindly pushed. Existing Android article rows store `originalUrl` and `feedName` but no feed URL. Do not infer source identity from a display name. Only backfill a record when both feed and normalized article identity are provable from persisted data; otherwise the first post-upgrade normal run may include a historic article once, disclosed as a migration limit. Add nullable `feedUrl` to digest article associations for future writes. Preserve every prior feed/history row. Room transaction covers history+ledger finalize.

iOS SwiftData: add optional `serverId`, `serverVersion`, `mutationRevision` default 0 to `Feed`; add persisted `FeedMutation` and `FeedSyncState` in V2, registered in `PersistenceController` with a tested V1→V2 migration. Add `ArticleDelivery` and generation diagnostics only in the later V2→V3 delivery migration. Keep cursor/server binding in the SwiftData singleton so reconciliation and cursor application use the same save transaction. Every pre-upgrade feed becomes a preserved full-field proposal regardless of its legacy dirty flag, following the identical initial full-reconciliation rules above. SwiftData must persist history and delivery identity together; if one save cannot guarantee this, use an explicit recovery journal and prove crash recovery before calling delivery committed. Root allocates exact migration file/model paths and owns schema ordering with IOS-DELIVERY. iOS existing `DigestArticle` records include both `feedUrl` and `originalUrl`: backfill provable normalized identities belonging to completed locally generated (`remoteId == nil`) digests, in the same migration/recovery transaction. Do not backfill remote, failed, missing-link or ambiguous records. Both platforms need upgrade tests with existing records and pending edits, and must never reset/delete a store as migration recovery.

## Implementation checkpoint — 2026-09-27

The staged source evidence above describes the original contract baseline. Integrated schema allocations are Alembic026–028, Room9–11, and frozen SwiftDataV1→V2→V3; current verification belongs in `docs/project-state.md`.

Android Room11 records nullable scheduled trigger, period, occurrence date and WorkRequest identity. Complete, partial, empty and deferred scheduled outcomes cover the exact occurrence; failed, cancelled and manual runs do not. Existing catch-up enqueue and WorkManager retry limits remain. New periodic work carries a fixed first-scheduled instant, saved schedule zone and durable anchor tag. Legacy unmarked work is updated in place once when ENQUEUED, preserving its ID and next due time; later registration leaves tagged work untouched. The worker uses nominal24-hour slots from that anchor in the saved zone, coalesces delayed intervals, and retains the original occurrence for retries. Boot registration retains its broadcast until selected WorkManager enqueue operations complete, with a bounded wait. Selection changes before child admission and during persistence cannot revive disabled work or cancel newly enabled work. Existing anchored inputs are never reset from a shifted next-run timestamp; pre-release intermediate tagged inputs without a saved zone retain their original anchor and current-zone fallback. This is durable coverage, not a promise of exact wall-clock dispatch or historical backfill.

Legacy article caps: new writes remain strictly0..2147483647. To keep older databases readable, FeedRead, v2 snapshots/conflicts and historical receipt replay project stored negative caps to0 and oversized caps toInt32max. Reads preserve raw values, timestamps, versions and receipt JSON; legacy no-op comparisons use the same public representation. A subsequent explicit cap write stores a valid value. Bindery applies the same projection when consuming a stored cap, so legacy rows do not fail the parser's strict argument validation. Raw stored values remain unchanged; new writes still require a valid cap. No schema change is involved.

Android periodic retry identity is the WorkRequest UUID plus the pinned WorkManager2.9 persisted periodCount, read through one isolated internal adapter off the main thread. Actual WorkerWrapper retry preserves the key and terminal acknowledgement advances it; neither wall-clock rollover nor a reused UUID may borrow another execution's outcome. Missing identity fails conservatively. Cancellation persistence completes before re-registration inspects/enqueues the same unique work. Reverify this dependency seam on WorkManager upgrades.

iOS interrupted-run recovery only accepts a prior edition's delivery claim for explicitly recorded manual regeneration. Generation mode is optional metadata in existing diagnosticsJSON; legacy/unknown mode requires the run's own claims and retains available failure/deferred diagnostics. This needs no SwiftData schema change. Completed runs are not reclassified; recovery tests explicitly seed an interrupted running marker.

### New-feed URL admission compatibility

New native feed admission validates hostname and port through the shared URL parser used only as a predicate. The exact input remains the feed key; no normalization is stored. Android and iOS apply the stricter check only when no exact persisted feed row exists. Snapshot decoding, durable wire replay and edits of known legacy keys retain their compatible shape check. Device syntax validation does not replace backend public-host/DNS admission or fetch-time redirect checks.
