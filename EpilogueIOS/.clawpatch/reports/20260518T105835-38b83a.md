minimum fix scope:

repro:
Return a sync digest whose filename is ../some-existing-file.epub, then run digest sync with EPUB downloads enabled; saveFile builds the target URL from that value and removes/writes that path.

## medium: Concurrent keychain saves can lose or reject the final value

id: fnd_sig-feat-service-f66db2df2c-c291_f7c52f88c3
category: concurrency
confidence: high
triage: confirmed-bug
status: open
feature: Digest Generation And Secrets (feat_service_f66db2df2c)

evidence:
- Modules/Data/Sources/Data/Services/KeychainService.swift:12-13 (KeychainService)
- Modules/Data/Sources/Data/Services/KeychainService.swift:30-31 (KeychainService.save(_:forKey:))
- Modules/Data/Sources/Data/Services/KeychainService.swift:43-47 (KeychainService.save(_:forKey:))

The service advertises Sendable and can be called from concurrent tasks, but save is implemented as delete-then-add. Two concurrent saves for the same key can interleave as delete/delete/add/add, causing one caller to fail with errSecDuplicateItem, or delete/add/delete/add, temporarily removing the secret and making readers observe nil. This is a real race at the API boundary because no actor, lock, or atomic SecItemUpdate/add fallback protects the compound operation.

recommendation:
Make save atomic: try SecItemAdd first, and on errSecDuplicateItem call SecItemUpdate without deleting; or serialize all operations behind an actor/lock. Do not ignore delete errors during a write path.

test analysis:
The included DigestGeneratorTests exercise only digest filename generation and EPUB output. There are no KeychainService tests, and no test performs concurrent same-key writes or read-during-write behavior.

suggested regression test:
Add a KeychainService concurrency test using a unique serviceName/key that launches many concurrent save calls for the same key, asserts no duplicate-item errors escape, and verifies the final value is one of the written values and never nil after successful completion.

minimum fix scope:
Update KeychainService.save(_:forKey:) to use add-or-update semantics atomically, and add focused tests for same-key concurrent writes.

repro:
Run two concurrent tasks that call KeychainService.save different values for the same key while a third task retrieves the key; depending on interleaving, one save can throw unableToSave(errSecDuplicateItem) or a retrieve can observe nil between delete and add.

confidence: high
triage: confirmed-bug
status: open
feature: Background Digest Jobs (feat_job_b612667f12)

evidence:
- App/Sources/Services/LocalDigestScheduler.swift:136-145 (LocalDigestScheduler.scheduleOvernightDigest)
- App/Sources/Services/LocalDigestScheduler.swift:538-539 (LocalDigestScheduler.nextScheduledDigestTime)
- App/Sources/Services/LocalDigestScheduler.swift:249-260 (LocalDigestScheduler.handleOvernightDigestTask)

Scheduling targets the next upcoming enabled period, including periods later today, and asks iOS to begin two hours before that window. recommendation:
Either schedule BGProcessing only for tomorrow's earliest period as the design describes, or persist/pass the intended target period from scheduling into the handler. test analysis:
LocalDigestSchedulerTests cover latestElapsedPeriod itself, but they do not cover the interaction between nextScheduledDigestTime, lead-time scheduling, and handleOvernightDigestTask period selection.

suggested regression test:
Expose/test a pure helper that resolves the generation period for a BGProcessing launch. Assert that with periods [.morning, .noon, .evening], a launch at 16:30 for an 18:00 scheduled window selects .evening, while a delayed launch after 18:00 also selects .evening.

minimum fix scope:
LocalDigestScheduler scheduling/period-selection logic and focused helper tests.

repro:
Enable noon and evening digests. At 15:00, schedule overnight digest; nextScheduledDigestTime is 18:00 and earliestBeginDate is 16:00. If iOS launches the BGProcessing task at 16:30, latestElapsedPeriod returns .noon, so generateDigest receives period: "NOON" instead of "EVENING".
